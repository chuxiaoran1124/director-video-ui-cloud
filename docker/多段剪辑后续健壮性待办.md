# 多段剪辑后续健壮性待办

## 背景

当前 `CW` 多段剪辑主流程已经可以完成：

- 生成段音频生成
- 生成段视频生成
- 素材进入拼接池
- 拼接成片
- 结果页回显

但下午内网偶发波动时，`Redis`/`MQ` 状态回写有概率超时，导致：

- 子任务实际已经提交到第三方
- 但本地 worker 因为状态写入失败，提前把子任务判失败
- 主任务因此停止在生成阶段，无法继续拼接

## 现象

典型日志：

- `redis.exceptions.TimeoutError: Timeout reading from socket`
- 出错点通常在：
  - `update_simple_task_status(...)`
  - `get_parent_task_id(...)`
  - `publish_cw_event(...)`

## 目标

把 `CW` 任务链改成：

- `Redis` 状态回写失败：只记日志，不影响主流程
- `worker_status` 回写失败：只记日志，不影响主流程
- `MQ` 结果事件发布失败：允许重试，或至少不直接把业务任务判死
- 真正决定任务成败的依据仍然是：
  - 第三方接口返回
  - 数据库落库结果
  - 最终素材是否成功生成/拼接

## 建议改造点

### 1. task_common_utils.py 增加安全包装

建议给以下操作统一套安全层：

- `redis_util.hgetall`
- `redis_util.hget`
- `redis_util.hmset`
- `RabbitMQUtils().publish`

建议新增：

- `safe_redis_hgetall(key, default=None)`
- `safe_redis_hget(key, field, default=None)`
- `safe_redis_hmset(key, mapping)`
- `safe_publish(queue, message, ...)`

行为：

- 捕获异常
- 打 warning/error 日志
- 返回默认值
- 不向上抛异常

### 2. update_simple_task_status / update_complex_task_status 降级

当前这两个函数直接依赖 Redis。

后续改造目标：

- 读旧状态失败时，直接退回模板对象
- 写新状态失败时，只记录日志
- 不抛异常给调用方

### 3. get_parent_task_id 降级

当前如果 Redis 抖动，拿不到 `parent_task_id` 可能影响事件回传。

建议：

- Redis 失败时直接返回 `None`
- 子任务继续跑
- 只是失去主任务事件同步能力，不应导致业务失败

### 4. publish_cw_event 降级

建议：

- `MQ publish` 失败只记录日志
- 不要影响已经完成的生成/拼接任务

后续如果需要更强保障，可再加：

- 本地数据库事件补偿表
- 定时补发机制

### 5. CW 子任务 finally 回写 worker_status 降级

以下任务的 finally 里都有：

- `cw_audio_task.py`
- `cw_video_task.py`
- `cw_splice_task.py`

建议把：

- `redis_util.hmset(material:worker_status:...)`

改成安全调用，避免 finally 阶段再抛错覆盖主异常。

### 6. executor.py 的主任务状态写入降级

`workflow/concatenation/scheduling/executor.py`

这里主任务会持续写：

- `task_key`
- `worker_key`

后续也应改成“状态失败不影响调度流程”。

## 优先级建议

建议按这个顺序做：

1. `task_common_utils.py` 安全包装
2. `cw_audio_task.py / cw_video_task.py / cw_splice_task.py` 接入安全包装
3. `events.py` 的 MQ 发布和清理降级
4. `executor.py` 主任务状态写入降级
