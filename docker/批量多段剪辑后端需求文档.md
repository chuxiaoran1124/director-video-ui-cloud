# 批量多段剪辑后端需求文档

## 1. 目标说明

这个功能要做的是一套**独立于原有 A2E 业务**的批量剪辑工作流。

它和原业务的关系是：

- 可以复用“批量生成视频”的能力
- 不能和原业务的数据、计划、任务互相串表
- 自己有独立的模板、计划、任务、素材标签和拼接规则

你现在的真实业务逻辑是：

1. 先选模板
2. 模板里是已经选好的几个文件夹和顺序
3. 计划执行时，先把所有生成段的视频都生成完
4. 再开始拼接段
5. 生成出来的视频要打标签，区分它是哪个计划、哪个节点、节点内第几个生成视频
6. 拼接时按全局最少重复原则选视频，尽量让素材组合不重复

所以这套设计的重点不是“模板 + 段”的抽象管理，而是：

- 模板 = 文件夹编排
- 计划 = 一次独立执行
- 生成 = 批量生成任务的一种节点
- 拼接 = 基于素材池和全局重复次数的选择任务
- 标签 = 标识素材来源和归属

---

## 2. 和现有后端模型的关系

你给的现有模型是：

- `material_a2e_plan_video`
- `meterial_a2e_task_plan_video`

这两个模型属于原 A2E 业务。

这次这个“批量多段剪辑”建议**不要复用这两张表做主业务表**，原因是：

- 原业务有自己的计划、任务、归档状态
- 这次的工作流是独立模块
- 如果混用，后面很容易互相影响、不好维护

建议只复用底层资源表：

- `media_folder`
- `media_file`

也就是：

- 文件夹还是素材池
- 视频还是视频素材本体
- 但“模板/计划/任务/标签/拼接规则”全部新建独立表

### 2.1 已核对的后端现状

这次我看了你当前后端代码后，结论是：

- `material` 负责和前端对接，这次的新模板、计划、任务接口也应该放在 `material`
- `scheduling` 负责任务执行，这次的新工作流编排、生成执行、拼接执行也应该放在 `scheduling`
- 现有批量生成入口会把 `A2EPlanVideoTaskList` 推到 `decompose_scheduled`，它会读写原计划任务表，所以本功能不能直接复用这张表当执行数据
- 拼接任务 `concat_add` 的 MQ 队列已经注册，入口在 `scheduling/service/task/execute_video_concat_add/concat_add_task.py`
- 拼接 API 封装在 `api/service/VideoAPIService/VideoAPIService.py` 的 `video_concat_add()`
- 但当前 `concat_add_task.py` 代理调用的 `handle_task.execute_video_concat_add()` 在代码里没有实际定义，README 里描述的核心函数目前需要补齐或迁移到独立模块

所以这次落地时不要只写 `material` 接口，还必须补一条完整的 `scheduling` 执行链路。

## 3. 真实工作流

### 3.1 模板

模板不是“公式模板”，而是“文件夹编排模板”。

模板里预先选好：

- 哪几个文件夹
- 顺序是什么
- 哪些节点是生成节点
- 哪些节点是拼接节点

### 3.2 生成节点

生成节点本质上是复用“批量生成视频”的底层能力，但不能直接复用原 A2E 计划任务表。

也就是说：

- 可以参考 `material/views/A2EPlanVideoViews`
- 可以参考 `material/service/A2EPlanVideoService`
- 可以参考 `scheduling` 里 `decompose_scheduled` 的执行拆法
- 但新功能要有自己的 workflow 任务表和自己的执行 service

这个节点会生成视频到某个目标文件夹里。

这个目标文件夹里的视频来源可能有三种：

- 本次计划新生成的
- 历史上已经生成过的
- 别的地方同步过来的上传视频

所以生成后不能只看“文件夹”本身，还要看**视频标签**。

### 3.3 拼接节点

拼接节点不是生成素材，而是从素材池里选素材来拼接。

拼接时要根据生成用途过滤：

- `现有直接拼接`
  - 本次新生成的视频不参与拼接
  - 只用文件夹里已有的历史视频和同步视频
- `仅新生成拼接`
  - 只用本次计划刚生成的视频
- `新+旧均拼接`
  - 这个文件夹里所有可用视频都参与
  - 但要走全局最少重复选择规则

### 3.4 执行顺序

这套工作流必须是：

1. 先把所有生成节点的视频全部生成完
2. 再统一进入拼接阶段

不能边生成边拼接。

## 7. 素材来源设计

第一版不单独建素材追踪表，直接在 `media_file` 上加工作流来源字段。

你的判断是对的：当前核心诉求只是区分“是不是本次计划生成的”，不需要为了这个单独维护一张追踪表。

所以判断规则可以简化成：

- `media_file.clip_workflow_plan_id = 当前计划 ID`：本次计划生成的视频
- `media_file.clip_workflow_plan_id IS NULL`：普通上传、同步或非工作流素材
- `media_file.clip_workflow_plan_id != 当前计划 ID`：其他计划生成的视频

再配合计划开始时间 `plan.run_time` 做过滤，就能确定“启动计划前已有素材”和“本次计划新生成素材”。

更稳一点的判断是：优先用 `clip_workflow_batch_no = 当前批次号` 判断本次执行新生成；如果第一版暂时不做多次执行/重试，再用 `plan_id + plan.run_time` 判断也够用。

## 7.1 `media_file` 建议新增字段

### 表：`media_file`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `clip_workflow_plan_id` | bigint | 生成来源拼接计划 ID，可为空 |
| `clip_workflow_plan_node_id` | bigint | 生成来源计划节点 ID，可为空 |
| `clip_workflow_task_id` | bigint | 生成来源工作流任务 ID，可为空 |
| `clip_workflow_batch_no` | varchar(64) | 本次执行批次号，重试或再次执行时用于区分 |
| `clip_workflow_node_order` | int | 来源节点顺序 |
| `clip_workflow_seq_no` | int | 节点内第几个生成视频 |

### 说明

- 第一版至少加 `clip_workflow_plan_id`，就能完成当前判断
- 我建议同时加 `clip_workflow_plan_node_id` 和 `clip_workflow_task_id`，方便查是哪一段、哪个任务生成的
- `clip_workflow_batch_no` 建议保留，因为同一个计划后面可能重试或再次执行，只靠 plan_id 容易混淆
- 普通上传、同步素材这些字段都为空即可
- 如果后面要做更复杂的素材血缘，再补独立追踪表也来得及

## 8. 拼接全局去重表

你提到的核心规则是：

- 在所有计划里，优先选“拼接次数最少”的视频组合
- 尽量保证素材不重复

这说明后端不能只在单个计划里做局部随机，必须有一张全局统计表。

## 8.1 视频组合使用统计表

### 表：`material_clip_video_pair_stat`

用于记录任意两个视频被拼接在一起的次数。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `video_a_id` | bigint | 视频 A |
| `video_b_id` | bigint | 视频 B |
| `pair_key` | varchar(128) | 组合唯一键，按 ID 小大排序后拼接 |
| `used_count` | int | 被一起使用的次数 |
| `last_plan_id` | bigint | 最近一次使用的计划 |
| `last_task_id` | bigint | 最近一次使用的任务 |
| `last_used_at` | datetime | 最近一次使用时间 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

### 说明

- 组合必须是无序的，也就是 A+B 和 B+A 算同一条

## 10. 具体执行逻辑

### 10.1 创建模板

1. 用户新建模板
2. 选择几个文件夹
3. 指定每个文件夹的角色：生成 / 拼接
4. 保存顺序

### 10.2 创建计划

1. 用户选择模板
2. 后端复制模板节点
3. 生成计划与节点快照
4. 计划状态为 `draft`

### 10.3 启动计划

建议后端分成两个阶段：

#### 阶段一：生成阶段

1. 找出所有 `node_role = generate` 的节点
2. 为每个生成节点创建 `material_clip_workflow_task`
3. 生成总数按 `base_video_count_snapshot × multiplier` 计算，例如 3 个基础视频，乘数 `*3`，最终生成 9 个
4. 由 `scheduling` 的新工作流生成任务执行实际生成
5. 生成的视频入 `media_file`
6. 在 `media_file` 上写入 `clip_workflow_plan_id`、`clip_workflow_plan_node_id`、`clip_workflow_task_id` 等来源字段
7. 生成完成后把该节点标记为 `generated`

#### 阶段二：拼接阶段

1. 所有生成节点完成后，才允许拼接阶段开始
2. 找出所有 `node_role = splice` 的节点
3. 根据 `generate_use_mode` 过滤可用素材，先得到基础数量
4. 拼接最终数量按 `基础数量 × multiplier` 计算
5. 计算候选组合的全局使用次数
6. 在满足用途过滤的前提下，选择“组合使用次数最少”的视频组合进行拼接
7. 更新 `material_clip_video_pair_stat`
8. 更新素材单体使用次数

5. 在 `material/urls.py` 注册模板、计划、任务、结果接口

`material` 层只做：

- 参数校验
- 模板和计划 CRUD
- 创建计划节点快照
- 启动计划时创建 workflow 执行任务
- 推送 workflow 编排任务到 `scheduling`
- 给前端查询状态、结果和错误

#### `scheduling` 层

1. 新增 `scheduling/service/task/execute_clip_workflow/`
2. 新增任务类型，例如 `clip_workflow_execute`
3. 在 `scheduling/service/mq_queue_const.py` 注册队列
4. 在 `scheduling/service/mq_dispatcher.py` 注册消费者入口
5. 工作流入口负责：
   - 锁定计划
   - 跑完所有生成节点
   - 等生成节点全部成功
   - 计算拼接候选
   - 创建拼接任务
   - 调用拼接服务
   - 回写结果、素材、统计

#### 生成任务实现

生成这里不能直接创建 `A2EPlanVideoTaskList`，否则就和原业务串表了。

第一版建议：

- 建独立的 workflow generate task
- 入参结构参考原 `A2EPlanVideoTaskList`
- 执行逻辑参考原 `decompose_scheduled`
- 回写只写 `material_clip_workflow_task` 和 `media_file`

如果底层生成能力目前强绑定 `A2EPlanVideoTaskList`，那就需要把生成服务拆出一个可复用的底层函数；原 A2E 和新 workflow 分别传自己的上下文进去。

#### 拼接任务实现

当前 `concat_add` 的队列和入口已有，但核心函数缺失，所以第一版有两个选择：

- 方案 A：补齐 `handle_task.execute_video_concat_add()`，并让它支持 workflow 回写
- 方案 B：不再走 legacy 代理，在 `execute_video_concat_add/concat_add_task.py` 里直接实现独立拼接逻辑

我更建议方案 B。

原因是：

- 新 workflow 的回写目标是 `material_clip_workflow_task` 和 `material_clip_workflow_splice_result`
- 不需要兼容老的未知表
- 避免再把所有逻辑塞回超长的 `handle_task.py`

拼接时仍然复用：

- `push_basic_task("concat_add", ...)`
- `VideoAPIService.video_concat_add()`
- Redis 回调 key：`video:post-production:concat_add:{data_id}`

但 `data_id` 建议使用 `material_clip_workflow_task.id` 或 `material_clip_workflow_splice_result.id`，并在 Redis 入参里带上 `workflow_plan_id`、`workflow_task_id`、`result_id`，方便回写。

### 10.5 三种生成用途的过滤规则

#### `existing_only`

- 只用当前文件夹中已有素材
- 排除本次计划刚生成的素材
- SQL 条件可以理解为：`create_time < plan.run_time`，并且 `clip_workflow_plan_id IS NULL OR clip_workflow_plan_id != 当前计划 ID`
- 例如当前文件夹原有 7 个，新生成 3 个，`existing_only` 的基础数量仍是 7，最终拼接数是 `7 × multiplier`

#### `new_only`

- 只用本次计划刚生成的素材
- 不允许使用历史生成或同步上传素材
- SQL 条件可以理解为：`clip_workflow_plan_id = 当前计划 ID`，并且 `create_time >= plan.run_time`
- 例如本次生成 3 个，`new_only` 的基础数量就是 3，最终拼接数是 `3 × multiplier`

#### `all`

- 当前文件夹内所有可用素材都参与
- SQL 条件可以理解为：`create_time < plan.run_time` 的历史素材，加上 `clip_workflow_plan_id = 当前计划 ID AND create_time >= plan.run_time` 的本次新生成素材
- 例如原有 7 个，新生成 3 个，`all` 的基础数量是 10，最终拼接数是 `10 × multiplier`
- 但排序时先按用途过滤，再按全局最少重复规则挑选

## 11. 首段优先与产出数量规则

当前前端只需要做“首段优先”。

也就是：

1. 找到模板中排序第一的有效节点
2. 根据它的 `generate_use_mode` 计算基础视频数
3. 最终计划产出数 = 首段基础视频数 × `multiplier`
4. 后续每一段都围绕这个产出数去补齐组合

举例：

- 首段文件夹原有 7 个视频
- 本次计划新生成 3 个视频
- 乘数是 `*3`

则：

- `existing_only`：基础数 7，最终产出 21 条
- `new_only`：基础数 3，最终产出 9 条
- `all`：基础数 10，最终产出 30 条

后续段不是简单随机取，而是在满足用途过滤后，优先选择全局重复度最低的组合。

现有两张底层表建议继续保留：

### `media_folder`

- 继续作为素材文件夹表

### `media_file`

- 记录哪些素材参与了哪个计划
- 通过 `media_file.clip_workflow_plan_id` 和计划开始时间判断素材是本次新生成还是历史素材
- 记录拼接组合的全局使用次数

## 15. 这版设计的关键点

如果只保留一句话，这版设计的核心就是：

> 模板选文件夹，计划跑两阶段，生成视频必须打来源标签，拼接按全局组合最少重复来选。

这几个点一定要保住：

- 模板和原业务独立
- 生成和拼接串成一个独立工作流
- 生成素材必须能通过 `media_file` 来源字段识别
- 拼接必须有全局去重统计
- 所有生成节点执行完成后，才能进入拼接阶段
